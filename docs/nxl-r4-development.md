# NXL R4 development contract

Core 0.2.34.dev0 keeps R4 separate from historical R3 resources and hashes.
`contracts/generate_r4.py` owns the closed schemas for 21 frames and seven
operation actions. `contracts/specification/nxl-r4-delta.json` preserves the
coordinated delivery specification. `--check` verifies generated bytes
without repairing drift; CI checks both R3 and R4 generators.

The manifest remains `development-partial`, and `R4_BUNDLE_EXECUTABLE` remains
false. A complete schema does not prove runtime authorization, host dispatch,
provider compatibility or distributed qualification. Remaining M01 work
includes complete operation/lease application conformance and
the complete shared consumer campaign. Neither host may enable product
execution on the strength of these decision tests.

## Runtime lease application

The authenticated host persists canonical grants and owns channel, lane,
consent and policy validation. The Core does not authenticate a network peer.
It creates the local request nonce and captures monotonic t0 before transport:

```python
attempt = await runtime.begin_r4_lease_request(
    scope=approved_scope, grant_id=grant_id, connection_id=connection_id,
    connection_generation=connection_generation, purpose="initial",
)
request = r4_lease_renew_frame(attempt)
grant = await authenticated_grant_exchange(request)
application = await runtime.install_r4_lease(attempt, grant)
await send(application.acknowledgement)
context = runtime.r4_operation_context(
    submit_frame, connection_id=connection_id,
    connection_generation=connection_generation,
)
```

`R4Authority` adds immutable session, workspace binding, credential, grant,
serial, connection and boot scope to `ExecutionContext`. `R4LeaseApplication`
returns that context and a fresh validated `lease.applied` frame. The runtime
requires its own registered attempt; copying an old grant into a new request
or changing t0 cannot extend a deadline. The full scope and source connection
are checked before effect. Removing or widening the installed metadata fails.
Preparing or opening an R4 session requires the installed context.

Productive expiry preserves previously granted `turn.interrupt`,
`runtime.close`, and strictly negative `approval.decide`/`input.provide`
replies. Negative replies must contain no operator response or response
reference and must still match the observed native request. Scope, action,
generation, boot and revocation checks remain mandatory; a peer cannot set
a containment flag. Replies carrying operator content are productive even
when their decision label is negative. The same classification applies at
the runtime and native writer boundaries.

A pending lease CAS remains a `LEASE_UPDATE_PENDING` fence for productive
operations. Core 0.2.28 releases session effect locks before awaiting storage
and preserves authorized containment during unchanged-scope renewal, as
specified below. Independent owned shutdown remains available when the
journal itself cannot admit public operations.

Use purpose `renew` on the same connection or `reconnect` with a newer
generation, then install the correlated grant. A live session renewal uses
the existing durable journal CAS. Cancellation detaches the waiter; it never
cancels a delivered producer. Retrying the same attempt can recover a lost
confirmation without another CAS or a new deadline. An expired candidate
cannot receive a successful application ACK.

`revoke_r4_lease(context, authorization_revision=...)` immediately closes
productive fences, including the native thread and pending spawn frontiers.
Its revision must exceed both installed and in-flight authority. Revocation
waits for an in-flight renewal and revokes the generation actually committed.
Busy or uncertain work yields no application ACK. Retry the same context and
revision to reconcile; a confirmed retry is idempotent. Physical containment
and outcome reporting still belong to the existing runtime lifecycle.

Initial installation is process-local, before any native session exists.
The host must persist canonical grant evidence. Core session claims and lease
CAS remain durable; the R4 request registry and monotonic deadline are never
restored as restart authority. A new runtime boot requires host reconciliation
and a new grant. This API does not implement Server grant issuance, daemon
multiplexing, canonical admission or provider qualification.

## Native approval and input

There are distinct hashes with distinct meanings:

| Field | Meaning |
|---|---|
| `operational_request.request_hash` / `payload.request.request_hash` | Original native adapter hash, 64 lowercase hex characters, unchanged. |
| `approval.request.request_hash` | `r4_operational_request_hash` over the complete operational proposal using JCS. It also covers params and the native local generation. |
| `operation.submit.intent_hash` | R4 semantic intent, including the complete decision payload and scope. |
| Core `OperationReceipt.intent_hash` | Existing native journal semantic, preserved for historical reads/idempotency. |

The operational proposal is retained intact, including `schema_version` when
present. Presentation redaction must use a separate copy. Native requests
require request ID, hash, method and params; extra authorization fields are
rejected. Claude requests also require the generation at application time.
Administrative proposals cannot be used as native decision operations.

`r4_native_decision_operation(frame, resolved_response=...)` produces a
`NativeApprovalOperation` for the public runtime API. It checks the native
request's action classification and the response digest. The digest is
`sha256:` plus SHA-256 of JCS response bytes, or null if there is no response.
For `response_ref`, the authorized host supplies the resolved content; missing
or changed content fails before a native runtime call. Unrelated expected
turn IDs are rejected: the native request already carries its actual target.

```python
from nexus_connector_core import (
    r4_native_decision_operation, project_r4_decision_receipt,
)

# The host has already verified its lane, grant, authority and session scope.
operation = r4_native_decision_operation(submit_frame)
receipt = await runtime.decide_native_approval(operation, execution_context)
wire_receipt = project_r4_decision_receipt(
    submit_frame, receipt, execution_context, operation, receipt_revision=1,
)
```

RuntimeCore still checks the currently observed pending request, granted
action, lease, namespace and generation. These conversion helpers grant no
authority. Notification `approval.decision` never applies native effects.
Only a canonical `operation.submit` may reach the call above.

Receipt projection requires the exact typed operation actually applied,
including response content when applicable. It verifies the native journal
hash and emits the distinct R4 hash. A projection error after native execution
retains `possible_effect=true`; it is not permission to retry under a new ID.
The Core journal does not persist raw operator answers. A host without a
protected recoverable answer must not promise reconstruction after a crash.

## Evidence boundary

### Close policy

R4 `runtime.close` requires `reason` (0–1024 characters), `drain_seconds`
(0–30) and `interrupt_seconds` (0–15). Interrupt reasons also accept the full
0–1024 character range. The host selects the close limits from canonical
authorization; the wire does not accept a free PID or signal.

Use `r4_close_operation(frame)` to preserve all three payload fields in the
typed `CloseOperation`. Its optional `policy` is a `ShutdownPolicy`;
omitting policy preserves legacy native journal hashes, but is refused when
closing with an installed R4 context. R4 receipt projection verifies the
reason and both timing values against the Core journal hash.

An explicit policy closes one session. After durable admission, drain fences
new productive effects and lease renewal for that session while containment
remains available. Drain and interrupt share one deadline, and a managed
resource's independent force worker cannot be delayed by a blocked send or
control lock. Attach never receives managed process force.

Waiters share one owned producer. Cancellation only stops observation. When
the deadline expires without a committed result, the API raises
`OUTCOME_UNKNOWN` with possible effect; it does not manufacture a receipt or
cancel physical work. The producer can later commit `SUBMITTED` under the
same ID after observed stop and owned-slot release. Query/replay that ID;
another close ID is not a retry strategy. Unknown ownership remains owned,
and unresolved producers keep global shutdown/factory disposal pending.

The deadline does not make blocked durable admission disappear: no public
close effect begins before its journal frontier. Independent owned-resource
shutdown remains the containment path when that admission is unavailable.
Provider and complete lifecycle qualification remain separate gates.

### Containment during pending lease CAS

The runtime drains existing native effects and reserves its productive hold
before delivering a renewal CAS. It releases the session locks before waiting
on storage. New productive effects recheck the hold after their lock and at
the effect frontier, so a blocked CAS cannot open a productive gap.

An installed R4 context can continue previously authorized interrupt, close,
or strictly negative native decisions during a same-scope renewal. The
pending grant must keep the exact scope, connection ID/generation and grant
ID, and must still permit that action. This applies after productive expiry
as well. A reconnect, scope change, removed action or revocation cannot borrow
the previous authority. An observed superseded durable owner remains fenced.

Late renewal cannot acknowledge a session already draining or closed. CAS
producers survive canceled waiters, and existing durable reconciliation still
decides confirmation loss. A blocked shared journal can independently delay
an operation's durable admission; owned shutdown remains the storage-independent
containment route. Tests holding the CAS port prove runtime lock independence,
not parallel transactions through an unavailable SQLite writer.

### Campaign scope

Tests exercise the real Core, SQLite journal, copied native adapter and a
strict subprocess peer for approvals and inputs. Both native and R4 entry
paths produce one response, return the same receipt on replay and preserve
native request bytes. Negative tests cover response tampering, wrong action,
scope/owner mismatch, altered operational params and unsupported fields.
The subprocess peer is a technical fixture, not a real provider campaign.

## Native domain capabilities

The R4 lease vocabulary remains the seven runtime operations. Domain actions
use a separate native capability ceiling. Trusted hosts bind the complete
12-field scope, connection ID and generation to the public
`ScopedNativeActionBridge` and the current RuntimeCore incarnation.
`r4_native_action_context` reads installed authority without granting a
runtime operation or extending its deadline. Unopened, revoked, draining,
expired or pending-renewal authority is refused; old contexts cannot survive
a successful renewal. Authorization is checked again after backend completion.
A mutation whose response crosses a fence has an unknown outcome and retains
its original operation ID.

`native_action_request_body` projects typed context/claim/complete requests
to the canonical HTTP DTO with bounded, detached JSON and unchanged identity.
The Core owns no handoff implementation, HTTP client or capability secret.
Automatic host launch, capability renewal and Pi socket lifecycle remain host
integration work. The R4 bundle remains development-partial and not executable.

## Owned Pi native action ingress

The public native_action_socket.PiNativeActionOwner supplies the trusted
pi_native_action launch callback. It checks the selected Pi adapter, prepared
capability reference and current context before and after listener startup.
One owner serves one session and cannot reopen after close.

NativeActionSocketService tracks socket observers and separate backend
producers. A request observation timeout or a cancelled close waiter never
cancels an admitted domain mutation. Retained producers count against the
admission limit even after clients leave. close(timeout_seconds=...) closes
admission and sockets, returning True only after all backend producers settle.
A False result means that the host must retain the owner and its dependencies.
Hosts must not infer safe retry from a timeout or socket loss. Unknown mutation
responses preserve the original operation ID.

The installed host campaign uses the copied Pi adapter, an owned Node process
and the packaged extension with a technical protocol peer. It does not qualify
the real Pi provider or enable automatic production execution.
