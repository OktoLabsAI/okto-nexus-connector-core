## C11-00 — Baseline e contrato da identidade

- HEAD de trabalho: `6909435` → `origin/main`; sem reset; tree limpa (apenas `=1` não-rastreado, preservado).
- Sementes reconstruídas das reproduções do revisor (nomes exatos, parametrizadas codex/claude): descoberta REAL pela API pública (`LocalRuntimeCore.discover(DiscoveryRequest((adapter_id,)))`, raízes confiáveis em PATH controlado, factory que proíbe open) + `evaluate_runtime_availability` + `to_dict()`.
- **Baseline registrado: 2 FAIL (AC11-01/02 — cópias byte-idênticas em alvos distintos projetavam linhas literalmente iguais: mesmo `candidate_ref` = fingerprint de conteúdo) + 3 PASS (controles AC11-03/04/05).** Idêntico ao revisor.
- Decisões de identidade (C11-00.02), publicadas em `installation.py`/`docs/api.md`:
  - **mesmo alvo canônico** (PATH duplicado/symlink resolvendo ao mesmo alvo) = **UMA** instalação (alias; discovery deduplica por ref);
  - **mesmo conteúdo em dois alvos** = duas instalações (refs distintas, MESMA identidade de build);
  - **rename/movimentação** = alvo canônico mudou → nova ref; a antiga fica stale (erro tipado) e exige resseleção;
  - **mudança de conteúdo (update)** = ref estável (mesmo alvo), evidência de build muda; prepare/open continuam recusando drift (AC11-10);
  - **dois hosts** = refs escopadas ao inventário do executor produtor; ref estrangeira não resolve (AC11-13).
  - Quatro identidades separadas: `adapter_id` (mecanismo) / fingerprint+`build_identity` (conteúdo) / **instalação selecionável** (ref desta correção) / **agente** (identidade canônica — permanece no Server).

## C11-01 — Referência local opaca e resolução única

- `src/nexus_connector_core/installation.py` (`INSTALLATION_REF_SCHEME = "nexus-install-v1"`): ref opaca e sem caminhos = sha256 de forma canônica com domínio+versão (esquema, `adapter_id`, executável canônico, `launch_script` quando presente). Realpath resolve aliases; alvo físico diferente → ref diferente; mesmo inventário repetido → refs estáveis (AC11-07); nunca índice/aleatório/display_name/agente/versão textual.
- `InstallationCandidate.installation_ref` (campo aditivo, default `None`): preenchido pelo discovery (`candidate()`, `candidate_pi_node_cli` — a instalação Pi é o par (node, cli.js)); `effective_installation_ref` deriva quando ausente (mesmo algoritmo).
- `discover_path` deduplica por **ref de instalação** (política de alias): nunca dois alvos distintos sob uma ref silenciosa, nunca escolha por ordem entre instalações distintas.
- `resolve_installation(candidates, adapter_id, candidate_ref)` — helper público de resolução: exatamente um candidato (caminhos ficam no host; alimenta `create_runtime(candidates=…)`/`prepare` existentes, que revalidam); zero → `INSTALLATION_REF_NOT_FOUND` tipado; >1 alvo distinto → `INSTALLATION_REF_AMBIGUOUS` tipado (resseleção, nunca `candidates[0]`); adaptador desconhecido → `CAPABILITY_UNSUPPORTED`. Nenhum spawn para resolver.
- Migração legada (C11-02.01): ref v1 (= fingerprint) resolve quando o inventário comprova exatamente um alvo; com duas cópias idênticas é ambígua por construção → erro tipado exigindo resseleção (AC11-11). Nenhuma chave/agente/histórico tocado.
